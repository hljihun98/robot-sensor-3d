# 개발 기록 — 센서 파손 3D 이력관리 (robot-sensor-damage)

이 앱을 고치기 전에 읽고, 고친 뒤에는 같은 커밋에서 이 파일도 고칩니다. 규칙은 저장소 최상위 [`CLAUDE.md`](../CLAUDE.md)에 있습니다.

## 개발 방향 — 바꾸려면 먼저 합의

| 원칙 | 내용 |
| --- | --- |
| 업무 로직은 한 곳 | 신고·승인·이력 규칙은 `public/js/core/`(특히 `service.js`)에만 둡니다. 데모 모드(브라우저)와 서버가 같은 코드를 씁니다. 화면(`views/`)이나 `server/`에 규칙을 따로 만들지 않습니다. |
| 두 가지 실행 방법 | ① 웹에서 바로(데모 모드, 브라우저에 저장) ② 내려받아 실행(서버 모드, SQLite). 둘 다 같은 화면 코드로 동작해야 합니다. |
| 기록은 지우지 않음 | 폐기·수리완료·종료는 상태 변경과 이벤트(`damage_events`)로 남깁니다. 영구 삭제는 잘못 등록한 호기에만 허용합니다. |
| 파손은 센서 실물에 | 파손은 센서(시리얼)에 붙습니다. 센서를 예비로 회수해 다른 호기에 달아도 이력이 따라갑니다. |
| 좌표·각도 규칙 | 단위 mm, 원점 = 센서 중심, 위 = +Y, 정면 = +Z. 각도는 위에서 볼 때 정면에서 시계 방향입니다(우측면 90° = −X, 좌측면 270° = +X). |
| 날짜 기준 보기 | 변화(CHANGED)는 그 날짜 이후에만, 정정(CORRECTED)은 과거 모습에도 적용합니다. |
| 확인 방법 | `npm test`(업무 로직 테스트)가 통과해야 합니다. 화면을 바꾸면 데모 모드(`npm run dev:static`)로 직접 확인합니다. |

## 다음 할 일 (우선순위순)

### 높음 — 데이터 손실·운영 문제

- [ ] **영구 삭제가 이력 있는 호기도 지움** — `public/js/core/service.js`의 `deleteRobot`. README는 "잘못 등록한 호기에 한해"라고 하지만 막는 코드가 없습니다. 2026-10-20에 재현: 18호기를 지우자 장착 이력 4건이 사라지고 신고 1건의 연결이 끊겼으며 번호를 다시 쓸 수 있게 됨. → 파손·신고·과거 장착이 있으면 거부.
- [ ] **폐기할 때 센서 처리를 안 고르면 "함께 폐기"** — `service.js`의 `disposeRobot`(`sensorActions` 기본값)과 `views/robot.js`의 폐기 창(첫 선택지가 "함께 폐기"). 고르지 않으면 현존 파손도 모두 종료됨(재현: 8호기 2건 → 0건). → 센서마다 선택을 필수로.
- [ ] **`.env`를 읽지 않음** — `package.json`의 `start`와 `server/config.js`. README대로 `.env`를 만들어도 무시되어 기본값 `HOST=0.0.0.0`(모든 네트워크에 열림)으로 뜹니다(재현: `PORT=3999` 무시). 실행 관리 홈페이지(런처)는 HOST·PORT를 직접 넘기므로 영향이 없습니다. → 시작 명령에 `--env-file-if-exists=.env`.

### 보통 — 보안·품질

- [ ] 사진 접근이 로그인만 확인 — `server/app.js`의 `/files/photos`. 승인 전 사진도 주소를 알면 열립니다(주소를 추측하기는 어려움). → 공개된 파손·본인 신고·관리자만.
- [ ] 세션 ID를 DB에 평문으로 저장, 비밀번호 최소 6자 — `server/app.js`, `service.js`.
- [ ] 서버 계층 테스트가 없음 — HTTP(세션·출처 검사·사진 저장)와 SQLite 저장소(`server/store.js`)는 테스트하지 않습니다.
- [ ] 트랜잭션이 실패해도 이미 저장한 사진 파일이 남음 — `server/runtime.js`의 `savePhoto`.
- [ ] 수리완료 후 되돌린(REOPEN) 파손은 과거 날짜 보기에서 수리 기간이 보이지 않음 — `service.js`의 `damageSummary`·`visibleAt`.
